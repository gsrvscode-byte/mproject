4. PROJECT INTRO — DETAILED VERSION (for deep-dive technical questions)
-----------------------------------------------------------------------
Let me walk you through the AI-Powered Policy PDF Parser project in
more detail. Insurance policy PDFs from different insurers vary a lot
in layout and structure, so we needed a way to reliably pull out
structured data — customer info, policy details, vehicle info,
coverage, nominee, discounts, and partner data — without manual data
entry. On the Node.js side, I built the upload API using formidable to
handle multipart PDF uploads, added validation, and orchestrated the
call to our Python/FastAPI service. On the AI side, I designed the
extraction prompts and JSON schemas sent to the OpenAI API, carefully
specifying the exact fields we needed so the output stayed structured
and consistent across different document formats. The two services
communicate over a clean JSON contract, and I containerized both with
Docker so they could be deployed and scaled independently. The result
was a fully automated document-processing pipeline that replaced what
used to be manual data entry, cutting turnaround time significantly
and reducing data-entry errors.

For the Insurance Management Platform, the core challenge was handling
multiple insurance products (Health, Travel, Motor, Two-Wheeler), each
with different insurer-specific business rules — things like
age-based eligibility, relationship validation between the policyholder
and dependents, medical declarations, and hospitalization checks. I
built this logic into the proposal processing pipeline so it applies
the correct rules dynamically based on product and insurer. On the
integration side, different insurers exposed REST, XML or SOAP
interfaces, so I built request/response transformation layers to
normalize everything into our internal data model, with structured
error handling so failures from one insurer's API don't break the rest
of the flow. On the data side, I used MongoDB aggregation pipelines and
indexing on frequently queried fields (like policy status and customer
ID) to keep proposal and reporting queries fast even as transaction
volume grew.
